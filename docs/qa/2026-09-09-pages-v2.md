## What v1 missed, and why

v1's stall test kept the mouse at a **fixed viewport point** while driving wheel ticks and let the
*page* scroll underneath it — a real technique, but it only proves the page scrolls; it never opens
anything and tries to scroll *that*. The owner's own workflow — click a project on the gallery wall,
try to scroll down inside the panel that opens — was never exercised. That gap is exactly where the
real bug was.

## The real bug: the case-study sheet couldn't be wheel-scrolled — on every route, every time

**Root cause, `src/components/gallery/ProjectModal.tsx`:** opening a project's case-study sheet locks
background scroll with `document.body.style.overflow = 'hidden'`. Lenis (the site's smooth-scroll
engine, `src/components/common/SmoothScroll.tsx`) attaches its own wheel listener on `window` and, by
default, captures **every** wheel event to drive its own smoothed page scroll — unless the element
under the cursor opts out with a `data-lenis-prevent*` attribute. The sheet's own scrollable numbers
panel (`overflow-y-auto`) never opted out. Result: a mouse-wheel gesture over the open sheet was
captured by Lenis, which then spent that gesture trying to move a page that cannot move (locked
behind the sheet) — the panel's own scroll never got the input at all. Touch was never affected
(Lenis's `syncTouch` defaults to `false`, so touch scrolling was always native), which is why this
read as "sometimes it's stuck" rather than "always."

This component is shared by **every** theme's Gallery section — Apple (`/`), Neo (`/neo`), Luxury
(`/luxury`), Brutalist (`/brutalist`), and Arcade's `#work` screen — so a single root cause explains
"gets stuck in a lot of places": it was the same interaction, repeated across five surfaces, any time
a visitor opened a project card with more content than fits the panel and reached for the mouse
wheel.

**Fix:** one attribute, `data-lenis-prevent`, on the sheet's scroller div. Lenis skips that node
entirely and the browser's native `overflow-y-auto` scroll takes the wheel input instead.

**Verified, not assumed** — measured with real `page.mouse.wheel()` input before and after, and
visually (screenshots in `sheet-fix/`), in English and Spanish, light and dark, at 1440×900 and
390×844:

| Locale/viewport/theme | scrollHeight | clientHeight | scrollTop after 15 wheel ticks (before fix) | scrollTop after (after fix) |
|---|---|---|---|---|
| en-US, 1440×900, light | 893 | 846 | 0 (stuck) | 47 |
| es-CO, 1440×900, dark | 929 | 846 | 0 (stuck) | 83 (fully reached bottom-of-scroll) |
| en-US, 390×844, light | 948 | 381 | 0 (stuck) | 567 |
| es-CO, 390×844, dark | 996 | 381 | 0 (stuck) | 615 |

Re-verified in the full harness run on every route that has a Gallery (Apple, Neo, Luxury,

true`. See "Sheet wheel-scroll" column below.

## Two suspects named in the task brief, investigated and cleared — not bugs

- **The Gallery carousel** (`data-lenis-prevent-wheel` on `.rail-wide` in `Gallery.tsx`, added when
  Lenis first landed): the working theory was that a vertical mouse-wheel gesture over a
  horizontal-only overflow container gets redirected by the browser into horizontal scroll,
  "stealing" the page scroll. **Measured directly** — drove a real wheel gesture with the mouse
  centered over the carousel's screen position after scrolling it into view via real wheel ticks
  (not `scrollTo`): `document.scrollY` advanced normally (2397px over 15 ticks) and the carousel's
  own `scrollLeft` never moved. The redirect does not happen in this browser/markup combination.
  Left unchanged — this pass's own new `findScrollSwallowers` check (below) also came back with 0
  swallowers on every route, corroborating it generically rather than for this one element only.
- **The Ticker's drag-scrub/skew-velocity coupling**: the concern was per-frame React state fighting
  the main thread. Read the component (`src/components/common/Ticker.tsx`) — it already drives
  everything through `useAnimationFrame` + Framer Motion motion values (`pos`, `useVelocity`,
  `useTransform`, `useSpring`); the only `setState` call is in a `ResizeObserver` callback, not the
  per-frame loop. `.ticker-mask` is `overflow: hidden`, not a real scroll container, so there is
  nothing for a wheel gesture to get trapped in. No change needed.

## "Giant blank spaces that lead nowhere": the Suspense fallback height, and what a full scan found

Apple and Neo lazy-load every below-the-fold section as its own chunk (`BuildTimeline`, `Process`,
`ShopifyWork`, `FleetMap`, `Gallery`, `Manifesto`, `Projects`, `Skills`, `StackByYear`, `Faq`,
`Contact`, `BuildHeatmap`, `CareerSubway` — 13 `Suspense` boundaries on Apple alone), and none of them
are gated behind an intersection observer — the import fires the moment the parent renders, i.e.
immediately on page load. Most of those fallbacks (`Pending`) defaulted to `min-h-[60vh]`; on
anything other than a fast local connection, a scrolling visitor can land on one before its chunk
resolves, and 60vh (≈540px at 900px viewport height, ≈506px at 844px) is a large, fixed-size blank
rectangle that then jumps to the section's real (usually shorter) height once it loads — a CLS event
stacked on top of a dead-feeling scroll. Arcade's own screen-loading fallback
(`ScreenLoading` in `Persona.tsx`) had the same shape at `min-h-[55vh]`.

**Fix:** capped the default at `min-h-[40vh]` in `src/pages/Apple.tsx`, `src/pages/Neo.tsx`, and
`src/pages/Persona.tsx` (`ScreenLoading`) — a small, one-line-per-file change, not a restructure.
Explicit per-section overrides that were already ≤40vh (8vh, 30vh, 40vh) are untouched.

**Honest limitation:** this pass did not throttle the network to force a chunk into its loading state
long enough to screenshot it — on this machine's localhost preview, chunks resolve inside single-digit
milliseconds, so the harness's own painted-window scan (below) never actually caught one *in* its
blank state; the fix is justified by reading the code (unconditional `lazy()` imports, no
intersection gating, generous fixed fallback height) and by the task's own explicit guidance, not by
a screenshot of a visible blank Suspense window. Flagged here rather than claimed as measured.

### New: a full-document painted-window scan (v2's "(B2)")

Built a scanner that walks the entire document height in 300px bands and, per band, samples a 6×8
grid via `elementsFromPoint`, checking each point for real paint (own text node, image/svg/canvas,
background-image, a non-transparent background-color, or a border) — not just "a content node's
bounding box roughly covers this range" (v1's `findGaps`), which can be fooled by a box that exists
but paints nothing at the sampled point. Run under `prefers-reduced-motion: reduce` for the same
reason v1's own gap-finder needed it: a `whileInView` reveal that just scrolled into a band can still
be mid-fade under normal motion, which would read as a false "blank."

**Result: 0 blank windows on every route, every Arcade screen, both viewports**, after the Suspense
cap above. The `Ticker`'s reduced-motion static list (flagged as an open observation in v1, ~300px
tall on Luxury mobile in this run) was re-checked visually — it is a readable wrapped list of ~8
store names with "En vivo" labels on a solid dark background, not blank. Confirmed a second time, not
the reported defect.

## New checks that came back clean (worth keeping in the harness anyway)

- **Scroll-swallower audit ("(C2)")**: every `overflow-x/y: auto|scroll` container whose height sits
  within 50–150% of the viewport gets a real wheel-over-it test (does `document.scrollY` still
  advance?), not a static flag. 0 swallowers found on any route at either viewport.
- **Chrome audit ("(D2)")**: footer (`footer[role="contentinfo"]`), top nav, and the design switcher
  present and visibly sized on every route and every Arcade screen (`[data-theme-switcher]` there).
  All present everywhere.
- **Real CLS ("(E2)")**: a `layout-shift` `PerformanceObserver`, read in a fresh, minimally-interactive
  context right after load settles — not on a page that has already been scrolled and clicked through
  by the rest of the harness, which would inflate the number with the harness's own interaction, not
  the page's. All routes land at 0.001–0.01 (desktop) and 0–0.006 (mobile); well inside "good."
  (An earlier draft of this check read `window.__cls` off the same page the wheel/sticky/modal tests
  had already run on and got 0.214 on Brutalist — that number was an artifact of the QA session
  itself, not the page; moving the read to `measureGeometry`'s own clean context fixed it. Recorded
  here so a future rerun doesn't reintroduce the same mistake.)
- **Images ("(E2)")**: 0 broken, 0 >300KB on every route. One methodology trap found and fixed in the
  harness itself: an offscreen `loading="lazy"` image the pass never scrolled to reads `naturalWidth
  === 0` — that is "not loaded yet," not "broken." An early draft flagged 58 of Apple's 78 images as
  broken this way; gated the check on `img.complete || a network response existed` first, which
  correctly reads 0 broken. Real, low-priority observation: several images (the Explore-grid design
  preview icon, and Brutalist's client-logo strip) don't carry explicit `width`/`height` attributes
  and aren't inside an `aspect-ratio`-boxed parent — a CLS risk in principle, but the measured CLS for
  those routes is 0.001–0.002, so it isn't manifesting as one in practice. Not fixed — no reflow to
  fix, and guessing at intrinsic sizes for third-party logo URLs is worse than leaving it. Worth a
  follow-up if any of those images are ever swapped for a slower host.
- **Failed requests ("(F2)")**: 0 real failures. One false positive found and fixed: `mailto:` links
  report as `requestfailed`/`net::ERR_ABORTED` in headless Chromium (no mail-client protocol handler
  to hand the "request" to) even though they are correct, working links in a real browser. Filtered
  to `http(s)` URLs only.
- **Overlaps**: one false positive found and fixed in the harness (not the page) — two
  `pointer-events-none` `fixed` decorative layers can overlap on screen without ever competing for a
  click, the same reasoning v1 already used for a negative-z-index background layer, just not scoped
  narrowly enough. Generalized the exclusion to "both sides ignore pointer events," not just one of
  them behind a negative z-index. 0 overlaps on every route after that.
